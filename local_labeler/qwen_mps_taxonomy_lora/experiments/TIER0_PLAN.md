# Tier 0 — план экспериментов («бесплатные» рычаги)

Серия контролируемых прогонов для QLoRA-разметчика reasoning-трейсов (Qwen3-8B 4-bit, MLX, Mac 32 ГБ).
Цель Tier 0 — выжать максимум из изменений, которые **не стоят дополнительной памяти и почти не стоят времени**
(≈ как текущий прогон, ~3–4 ч на эксперимент), прежде чем трогать дорогой рычаг `num_layers` (это Tier 1).

> **Главный принцип: один фактор за прогон.** Все изменения Tier 0 вносятся НЕ сразу.
> Каждый эксперимент меняет ровно одну вещь относительно предыдущей лучшей конфигурации.
> Иначе при росте метрики мы не сможем сказать, что именно сработало, и план перестаёт быть экспериментом.

## 2. Метрики успеха (переопределяем!)

`flat_macro_f1` для отбора экспериментов **не используем** — она маскирует главную проблему. Следим за:

1. **Primary — mean per-field macro-F1** по всем 37 полям (база = 0.667). Главный критерий «лучше/хуже».
2. **Secondary — mean macro-F1 по 14 схлопнувшимся полям** (база ≈ 0.48). Сюда бьём в первую очередь.
3. **Guardrail — mean macro-F1 по «хорошим» полям** (те ~13 полей, где F1 > 0.8). Не должен заметно просесть
   (особенно важно для E3: oversampling может испортить уже хорошие поля).
4. **Sanity — prediction_ok_rate** (должен остаться 1.0) и **row_exact_match** (холистическая проверка).

> Изменение принимается, если выросла метрика (1) **и** не обвалился guardrail (3).
> `evaluate_predictions.py` уже даёт per-column — нужно лишь усреднять по нужным подмножествам полей.

## 3. Preflight (шаг 0) — заморозить данные

Перед любыми прогонами фиксируем датасет **один раз**, чтобы все эксперименты делили идентичный сплит:

- Разобраться с рассинхроном: `manifest.json` пишет `n_train=6767`, но текущий `train.jsonl` = 5544 строки
  (рядом лежат `*.jsonl.full` на 6767). Перегенерировать данные с фиксированным seed=42 и **задокументировать** итоговые `n_train/n_valid/n_test`.
- После заморозки `valid.jsonl` и `test.jsonl` **не меняются ни в одном эксперименте**.
  В E3 (oversampling) меняется **только `train.jsonl`** — valid/test остаются теми же, иначе метрики несравнимы.
- Все эксперименты оцениваются на одном и том же `test_source.csv`.

## 4. Фиксированные константы (одинаковы для E0–E3)

Чтобы прогоны были сравнимы, всё, кроме изучаемого фактора, держим неизменным:

| Параметр | Значение | Зачем фиксируем |
|---|---|---|
| model | `./models/qwen3-8b-4bit` | одна база |
| **num_layers** | **4** | НЕ трогаем в Tier 0 (это рычаг Tier 1) |
| batch_size / grad_accum | 1 / 8 (эфф. батч 8) | как в baseline |
| **max_seq_length** | **3072** | инфраструктурная оптимизация: p95≈2660 ток. → усечения почти нет, но память/время меньше. Ставится сразу всем — это НЕ изучаемый фактор |
| iters | **1400** (~2 эпохи: 5544/8≈693 ит/эпоху) | равный бюджет обучения у всех |
| grad_checkpoint | true | обязателен на 32 ГБ |
| dropout | 0.05 | как в baseline |
| mask_prompt | true | loss только по JSON |
| seed | 42 | воспроизводимость |
| prompt_style | compact | как в baseline |

Каждый эксперимент пишет в **свой** `adapter_path` и **свой** файл метрик (не перезаписываем!):
`adapters/tier0_E*/` и `predictions/metrics_E*.json`.

## 5. Эксперименты

Цепочка инкрементальная (greedy): каждый следующий строится поверх **победителя** предыдущего шага.
Если эксперимент не улучшил метрику — откатываемся, и следующий строится на прошлой лучшей конфигурации.

### E0 — Контроль (baseline на новой инфраструктуре)
- **Суть:** текущие гиперпараметры обучения (`lr=1e-5` константа, `rank=8`, `scale=20`, без oversampling),
  но на зафиксированной инфраструктуре (`seq=3072`, `iters=1400`, замороженный сплит).
- **Назначение:** честная точка отсчёта для атрибуции. Отделяет эффект смены `seq/iters` от эффекта смены `lr`,
  и подтверждает, что результат воспроизводится.
- **Меняем относительно прод-модели:** только инфраструктуру (seq 4096→3072, iters 1125→1400). Гиперпараметры обучения те же.
- **Можно пропустить**, если считаете эффект `seq/iters` пренебрежимым — тогда базой служит существующий
  `metrics.json` (0.667), но сравнение с E1 будет включать небольшой конфаунд. Для курсовой E0 рекомендуется.
- **Время:** ~3–3.5 ч.

### E1 — Learning rate + cosine (проверка H1: недообучение)
- **Суть:** поднять `learning_rate` 1e-5 → **1e-4** и включить расписание **cosine + warmup** (вместо константы).
- **Назначение:** проверить, что модель была недообучена из-за слишком низкого LR. Самый дешёвый и вероятный источник прироста.
- **Меняем относительно E0:** только LR и наличие расписания. Всё остальное идентично.
- **Ключевые параметры:**
  ```yaml
  learning_rate: 1e-4
  lr_schedule:
    name: cosine_decay
    warmup: 50
    arguments: [1e-4, 1400, 1e-6]
  ```
- **Что измеряем:** mean per-field macro-F1 vs E0. Ожидание: общий подъём, особенно на полузахлопнувшихся полях.
- **Риск:** при слишком высоком LR — нестабильность/расхождение loss. Если train loss скачет — пробуем 5e-5.
- **Время:** ~3–3.5 ч.

### E2 — Rank 8 → 32 (проверка H2: ёмкость адаптера)
- **Суть:** увеличить `rank` LoRA 8 → **32** (память почти не растёт: адаптер +~30 МБ, скорость ≈ та же).
- **Назначение:** проверить, упирается ли качество в ёмкость адаптера поверх исправленного LR.
- **Меняем относительно E1 (победителя):** только `rank`. **`scale` оставляем = 20**, чтобы изолировать именно ранг
  (масштаб — отдельный возможный микро-эксперимент, здесь его не трогаем).
- **Ключевые параметры:**
  ```yaml
  lora_parameters:
    rank: 32
    dropout: 0.05
    scale: 20.0
  ```
- **Что измеряем:** прирост vs E1. Если близко к нулю — ёмкость не была узким местом (вероятный сигнал, что упор в `num_layers` → Tier 1).
- **Время:** ~3–3.5 ч.

### E3 — Oversampling редких классов (проверка H3: дисбаланс)
- **Суть:** на уровне данных увеличить представленность строк с редким классом по 14 схлопнувшимся полям
  (дублирование/взвешивание строк в `train.jsonl`), valid/test не трогаем.
- **Назначение:** прицельно лечить мажоритарный коллапс — главную причину низкого mean macro-F1.
- **Меняем относительно E2 (победителя):** только обучающую выборку (`train.jsonl`). Гиперпараметры из E2.
- **Стратегия (простая и прозрачная, без правки тренера):**
  - для каждого схлопнувшегося поля строки с его редким значением получают вес ∝ обратная частота класса;
  - вес строки = max по всем целевым полям; дублируем строки пропорционально весу;
  - **кап на раздувание** train ≤ 1.5× (чтобы эпоха не выросла сильно); при 2 эпохах iters пересчитать.
- **Важный нюанс (почему это эксперимент, а не гарантия):** задача multi-label — дублируя строку ради одного
  редкого поля, мы меняем распределение 36 остальных. Поэтому **обязателен guardrail**: следим, не просели ли
  «хорошие» поля. Если просели сильно — снижаем кап или переходим к взвешиванию loss (это уже Tier 1+).
- **Что измеряем:** mean macro-F1 по 14 схлопнувшимся полям (главное) + guardrail по хорошим полям.
- **Время:** ~3.5–4.5 ч (train чуть больше).

> **Альтернатива oversampling'у** (на будущее, не Tier 0): взвешивание loss по редкости класса — чище,
> но требует модификации тренера MLX-LM. В Tier 0 намеренно берём data-level подход, т.к. он «бесплатный».

## 6. Протокол одного прогона

Для каждого эксперимента (пример для E1):

```bash
cd qwen_mps_taxonomy_lora
source .venv/bin/activate

# 1) Обучение по конфигу эксперимента (свой adapter_path внутри yaml)
mlx_lm.lora --config ./configs/tier0_E1.yaml

# 2) Инференс на ЕДИНОМ тесте, в отдельный файл
python scripts/infer_mlx.py \
  --input ./data_mlx/test_source.csv \
  --output ./predictions/test_pred_E1.csv \
  --model ./models/qwen3-8b-4bit \
  --adapter-path ./adapters/tier0_E1 \
  --prompt-style compact --max-tokens 900

# 3) Метрики в отдельный json
python scripts/evaluate_predictions.py \
  --predictions ./predictions/test_pred_E1.csv \
  --out-json ./predictions/metrics_E1.json
```

Отбор лучшего чекпойнта (с учётом того, что инференс на Mac медленный):
сначала смотрим val loss из лога обучения, берём 2–3 поздних чекпойнта, и только им считаем
полную macro-F1 на `valid_source.csv`; победителя — гоняем на `test`.

## 7. Правила принятия решений

- После E1: если mean per-field macro-F1 вырос — E2 строится на E1; если нет — E2 строится на E0, а гипотеза H1 отклонена.
- После E2: аналогично выбираем базу для E3 (E2 или E1).
- После E3: финальная конфигурация Tier 0 = лучшая из {E0, E1, E2, E3} по primary-метрике при выполненном guardrail.
- Любой эксперимент, уронивший guardrail (хорошие поля) более чем на ~3 п.п. при сомнительном выигрыше — откатываем.

## 9. Что НЕ входит в Tier 0 (явно отложено)

- `num_layers` 4 → 16/24 — главный, но **дорогой по времени** рычаг → Tier 1.
- DoRA вместо LoRA → Tier 1 (ablation).
- batch_size > 1, distributed/2-GPU → не используем (только 32 ГБ Mac).
- Взвешивание loss, специализированные адаптеры, few-shot в промпте → Tier 1+.

---

### Итог по объёму
E0–E3 = 3–4 прогона × ~3–4 ч ≈ **12–16 ч** суммарно (overnight × 2). E0 опционален → можно уложиться в ~9–12 ч.
Порядок (LR → rank → данные) выбран так, чтобы сначала исправить базу обучения, а уже на ней мерить остальное.
